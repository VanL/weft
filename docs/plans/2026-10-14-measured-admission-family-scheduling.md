## Goal

Replace the 0.9.110 ordinary-child lane and lifetime connection reservations with measured admission and a small, bounded depth-first scheduler. Ordinary requests remain in `weft.spawn.requests`. FIFO orders independent work; LIFO favors descendants within an active branch. `weft.state.labels.<root_tid>.pending.<parent_tid>` provides consume-on-dispatch per-parent pending queues that empty and auto-disappear in SimpleBroker as children are launched, while detached running task lineage and Manager frontier checkpoints live in the existing `weft.state.tasks.<tid>` runtime state queues (`[OBS.6]`). Queued tasks consume no process or connection allowance. No task declares its future child count.

The key bound is on concurrently open branches, not the number of messages in the durable backlog. A branch retains its place while a task initializes or works before submitting a descendant. Its descendant can extend that branch; a sibling needs another free branch place. This prevents delayed child submission from turning a LIFO queue into breadth-first process creation.

- [x] Ordinary CLI, client, and runtime submissions all use the primary source and the existing reservation/launch/ack path.
- [x] PostgreSQL admission uses coherent measured pressure, with one global operating reserve and no per-task prospective connection debt.
- [x] Five branch frontiers per Manager by default; FIFO independent admission, round-robin active frontiers, LIFO descent, and spare-frontier sibling parallelism.
- [x] Family pending queues are incremental, consume-on-dispatch, and auto-disappearing; detached task lineage reuses `weft.state.tasks.<tid>` so dispatch never reconstructs the entire task graph or requires manual table garbage collection.
- [x] A finite rollup → enrichment → LLM workload drains under a stated resource envelope, including delayed child submission and early rollup exit.
- [x] Recovery, multiple Managers, pipelines, queue cleanup, and migration preserve accepted TIDs and expose the limits of the guarantee.

## Evidence and the workload to prove

Read-only ops investigation found a deployed 0.9.110 Manager, SimpleBroker 8.7.0, and simplebroker-pg 4.7.0; inspected core source hashes matched this baseline. At 2026-10-14 12:21:55 UTC, 60 LLM tasks were queued and 43 enrichment starts followed the oldest LLM submission, with no LLM starts in that observation. The shared children FIFO had recreated the parent/child ordering problem one level deeper. A later reconstruction combined 130 observed connections with 137 budget deficits, producing 267 accounted connections. That reconstruction used retained Manager evidence and is not a direct observation of its instantaneous in-memory decision.

The local application source establishes the actual execution shape:

- `../mm-governance/agents/monitoring/wazuh/case_rollup/run.py::run` submits reconciliation work and returns; rollup does not join all enrichments.
- `../mm-governance/opsweb/apps/monitoring/services/weft_submissions.py` submits on transaction commit and rejects `wait=True` for those submissions.
- `../mm-governance/agents/monitoring/llm_call.py::call_structured_llm_task` submits the LLM task and then calls `task.result()`.
- The application's existing `metadata["family"]` is a domain classification. Never repurpose it as scheduler ancestry.

Therefore a family's pending work must survive its root's exit, and a running enrichment must retain a path for a child that has not been submitted yet. Neither fact requires predicting a child count or building a general wait-for graph.

The algorithm follows depth-first task scheduling and bounded work sharing. Fair scheduling across independent computations is analogous to per-flow scheduling. References: [Cilk runtime and deques](https://www.usenix.org/legacy/publications/library/proceedings/ana97/full_papers/blumofe/blumofe_html/node2.html), [deficit round robin](https://web.stanford.edu/class/ee384x/EE384X/papers/DRR.pdf), and [SEDA overload control](https://www.usenix.org/legacy/event/usits03/tech/full_papers/welsh/welsh_html/usits.html). Weft retains blocking OS processes, so Cilk's space/progress theorems do not transfer without the resource assumptions below. Do not implement DRR, a general graph engine, or continuations for this slice.

## Design

### 1. One measured admission gate

For ordinary work:

```text
U = get_connection_usage(...)["total"]
C = configured applicable connection ceiling
R = existing configured operating reserve
available = max(0, C - R - U)
admit one eligible launch only when available > 0
```

Use a fresh coherent public SimpleBroker observation outside an encompassing caller transaction. `by_owner` provides attribution and diagnostics, not credits to subtract from `total`. Unattributed and external pressure stays in U. Match C and U's scope: the current API returns server-wide pressure; a lower configured role ceiling with server-wide U is conservative, not an exact per-role meter. Do not issue private PostgreSQL catalog queries to invent a second measurement contract.

This restores measured admission, not a promise that a new task needs exactly one connection. No arbitrary command can declare all future connections automatically. The configured reserve and bounded launch/branch growth absorb variation; PostgreSQL enforces its actual limit. Admission remains a soft guard across processes and external clients. Unknown/failed accounting denies new launches, preserves accepted work, and retains the existing bounded retry and responsive control/reap paths.

Keep the existing internal service/pipeline eligibility and reserve policy: internal requests may use the operating reserve under their existing ceiling. Their observed connections are included in U. This plan removes the ordinary child lane, not the pre-existing internal runtime lane. The progress envelope includes internal use; internal work does not have an unlimited connection budget.

Remove `postgres_accounted_usage`, `connection_budget`, `WEFT_ADMISSION_TASK_CONNECTION_BUDGET`, deficit restoration on close, lifetime debt, and budget-recovery caches. A default `weft run ls` has no eight-slot charge. Preserve process-scoped SimpleBroker owner labeling, runtime context custody, and scoped wrapper/worker liveness evidence independently of the removed AdmissionRecord.

Reuse the current single launch-worker path. Do not dispatch a burst against one sample. After each ordinary launch commits on the Manager reactor (`launched_ns`), gate the next ordinary dispatch across reactor turns (never via a blocking sleep) until one of three explicit release conditions holds, then sample `U` again before dispatching the next ordinary candidate:
1. **Positive startup evidence**: a valid `weft.state.tasks.<tid>` runtime snapshot (written by `BaseTask` after owner-label binding and initial queue setup) is observed, or PostgreSQL `by_owner` reports positive attributed connections for the task's `connection_owner`. Command tasks (`weft run ls`) whose child subprocess never opens a broker connection satisfy this branch as soon as the `Consumer` wrapper publishes its initial `weft.state.tasks.<tid>` row.
2. **Early exit or launch failure**: the launched wrapper exits (`not process.is_alive()`) or settles through the existing child-sentinel/launch-failure reap path.
3. **Bounded missing-snapshot fallback**: initial `weft.state.tasks.<tid>` publication is best-effort (`BaseTask._register_tid_state`), and liveness grace is not a readiness deadline. If `MANAGER_ADMISSION_RECHECK_SECONDS` elapses after `launched_ns` while `process.is_alive()` remains true and no snapshot is visible, the Manager performs one direct snapshot retry; if `weft.state.tasks.<tid>` is still absent, it retains the live task in its local resident/frontier state and its own durable `weft.state.tasks.<manager_tid>` checkpoint using launch-time `RuntimeIdentity` (`root_tid`, `submitter_tid`, `ancestry_tids`, `scheduling_class`, `connection_owner`) and scoped process identity (`hostname`, `(pid, create_time)`). It logs a rate-limited diagnostic (`startup_feedback_snapshot_missing`), refreshes `U`, and clears the inter-launch gate (releasing the startup frontier if `scheduling_class == "background"`). Missing task snapshot publication alone therefore does not stall subsequent dispatches. First observed usage is not a promise of final pool size; missing owner counts or missing initial snapshots are never death evidence.

Clearing the startup gate does **not** acknowledge the reserved request. Before another ordinary dispatch, either task-owned snapshot/positive settlement evidence must resolve launch custody, or the Manager's post-launch checkpoint must have been successfully published. A failed checkpoint write retains the reservation and gates further ordinary dispatch while bounded maintenance retries; controls and reaping continue. Section 3 defines the handoff and cleanup rules using the existing reservation/checkpoint pair.

SQLite retains its existing actual live/unknown TID accounting, unioned with local launches; it does not import PostgreSQL inspectors. The same ordinary scheduling policy runs on both backends. Preserve the existing disabled-admission setting: it disables the resource gate, not family classification or the configured scheduling bound.

### 2. Bounded FIFO/LIFO scheduling

A **frontier** is a Manager's bounded place for progressing one ancestry branch. It carries an anchor TID and a stack of ordinary task ancestors through the current tip. The initial limit W is 5 per Manager, configurable as the positive integer `WEFT_SCHEDULER_MAX_FRONTIERS`; define its default and validation in `_constants.py`. It is a concurrency policy, not connection currency. Increasing it increases possible throughput and the required progress envelope.

The rules are deterministic:

1. Independent pending families are ordered FIFO by original root request ID, with request ID breaking ties. An inactive family with late-discovered work rejoins at that original position. Active frontiers receive round-robin turns, preventing a continuously producing branch from monopolizing launch selection. IDs define broker ordering, not wall-clock acceptance order when a caller supplies an older explicit TID.
2. A free frontier first admits the oldest pending independent family. With no such family waiting, it may take an unassigned sibling subtree from an active family. Choose families round-robin and the oldest stealable sibling, exposing older work to spare capacity.
3. A frontier serves an eligible direct child of its current tip LIFO by original request ID. Descending pushes the child onto the same frontier. It does not consume a second frontier.
4. While that tip initializes or performs work before spawning, its place remains occupied. Another sibling cannot use the same frontier. A spare frontier can run the sibling in parallel. This is the essential difference from merely popping the newest message repeatedly.
5. Pop an exited tip only after the existing scoped process/reap rules establish it is no longer resident. Retain its logical membership independently of the live stack. Offer its known pending descendants at the nearest still-resident ordinary ancestor, or the logical family root if none remains. Cache this contracted scheduling parent; do not walk the full ancestry on every selection. A child of an exited ancestor can extend a matching tip, but needs a spare frontier if it would fork a live path.
6. Reuse a frontier immediately for known eligible work in its branch/family after popping the tip. If it covers no live path and has no known unassigned work, return it without waiting for a source sweep. A borrowed frontier may return when its exclusive live path and known work are gone; shared ancestors stay covered by another frontier. Prefer a waiting independent family before borrowing a new sibling. A terminal event alone never establishes process exit.
7. Logical membership can outlive all of a family's active frontiers. A late-discovered descendant rejoins the family pending index and obtains a free frontier in FIFO order, or extends a matching active tip. It cannot acquire an extra branch place merely because its producer exited. Periodic source reconciliation is amortized across turns, never triggered by each leaf completion or frontier reuse.

All full TaskSpecs remain on `weft.spawn.requests` until actual dispatch. The scheduler chooses an exact message ID, checks admission, and uses SimpleBroker's existing atomic exact-ID move to `T{manager}.reserved`. A lost move race drops that candidate and retries selection. The existing validator, seed, launch, terminal-error, and acknowledgement code remains the only execution path. Extend the Manager's inherited `_fetch_next_message` selection seam, not generic watcher ordering for unrelated consumers.

Malformed JSON, envelopes, TaskSpecs, or lineage enter a bounded invalid-candidate list keyed by source ID. Reserve them through that same exact-ID path and run the existing canonical validation/terminal-error/ack handling. They never call `Process.start` or retain a frontier. Validation-only rejection can proceed while resource admission is closed; a request found valid must return to ordinary eligibility rather than launch through this exception. Reuse the transport validator, not a second schema. Uncertain classification is retried, not silently dropped or treated as invalid. Test invalid rows ahead of valid required descendants.

The bounded structures are the W active frontiers and their launch-ready candidates. The durable pending backlog is not capped at five or charged for processes. Classification must keep advancing while admission is blocked, so a child behind a large root backlog becomes selectable. Never fill a five-row FIFO lookahead and wait for those rows to launch before discovering descendants.

No public submit failure or producer blocking is added solely because all frontiers are occupied. Existing queue-first acceptance remains intact. This is backpressure on process creation. Disk/backlog quotas and application-level rejection are separate work.

### 3. Queue-native pending indexes and detached-task lineage

#### Why lineage must be broker-backed while pending queues must auto-disappear

Two architectural properties of Weft govern how family state is stored:

1. **Launched tasks are separated from both their submitting parent's and the Manager's OS process trees**:
   - When a parent task (`rollup` or `enrichment`) submits a child (`enrichment` or `LLM`), it does not fork or spawn an OS child process; it writes a spawn request to SimpleBroker and the Manager spawns the child `Consumer` via `weft/core/launcher.py::launch_task_process`. Thus `os.getppid()` never reflects logical task ancestry.
   - Ordinary user tasks are launched with `daemon=False`, detached standard streams, and `stop_with_parent=False` (`weft/core/launcher.py::_task_process_entry`). By design ([MA-1], [MA-3]), running user tasks survive Manager drain, idle exit, crash, or supersession and continue executing outside any successor Manager's `self._child_processes` handle map.
   - Furthermore, intermediate ancestors can exit while both an older ancestor and a deeper descendant remain active (for example, `R → A → B → C` under `W=1`, where `B` submits `C` and exits while `A` waits for `C`). Once `LivenessMonitor` deletes `B`'s task snapshot and the old Manager's checkpoint, `(root_tid=R, submitter_tid=B)` alone would lose the `B → A` link and prevent a replacement Manager from placing `C` beneath `A`'s occupied frontier. Likewise, once the Manager checkpoint disappears, recovering live tasks from `weft.state.tasks.<tid>` without their validated lifecycle class (`finite`, `background`, `internal`) would misclassify persistent/interactive workers as occupied finite frontiers.
   - Therefore, accepted requests, `RuntimeIdentity`, and `weft.state.tasks.<tid>` snapshots must carry the immutable finite ancestor chain (`ancestry_tids`) and validated `scheduling_class` alongside `root_tid`, `submitter_tid`, and scoped process identity (`host_processes` / `runtime_handle`) so a successor or peer Manager can reconstruct live detached branches without relying on in-memory `BaseProcess` handles, OS `ppid` trees, or dead intermediate snapshots.
2. **SimpleBroker queues are auto-created and auto-disappearing when consumed — not relational tables**:
   - In SimpleBroker, queues are created on first write and vanish automatically when their last message is consumed (`move_one` or `delete`).
   - An earlier draft of this plan proposed an append-only `weft.state.labels.<root_tid>` queue storing `member` lifecycle facts (`accepted`, `launched`, `snapshot`, `terminal` with foreign-key `source_ref` pointers) and `frontier` revision/tombstone records, while leaving `pending` rows unconsumed in `.pending.<submitter_tid>` until a four-condition family retirement fence manually garbage-collected them via `exact-delete`. That turned SimpleBroker queues into unconsumed event-sourced relational tables and duplicated state already owned by `weft.state.tasks.<tid>`.
   - Instead, each runtime concern stays with its single queue owner and empties through its natural lifecycle:

| Queue / Owner | Contents and lifecycle |
| --- | --- |
| `weft.state.tasks.<tid>` (Task-owned, `[OBS.6]`) | Complete task runtime snapshot (`BaseTask._build_tid_state_payload`), extended to include immutable `root_tid`, `submitter_tid`, `ancestry_tids` (ordered finite ordinary ancestor TIDs from `root_tid` through the nearest finite ordinary ancestor at submission time), validated `scheduling_class` (`"finite"`, `"background"`, or `"internal"`), and `connection_owner` alongside existing `runtime_handle`, `host_processes`, `hostname`, and `terminal`. Survives Manager turnover; deleted solely by `LivenessMonitor` when the detached task process is proven dead (`[LIVENESS.R3]`), so the queue auto-disappears on task exit. |
| `weft.state.tasks.<manager_tid>` (Manager-owned, `[OBS.6]`) | Manager runtime snapshot (`Manager._build_tid_state_payload`), replacing `admission_launches` with `scheduler_frontiers` (active frontier stacks `[anchor_tid, ..., tip_tid]` and retained resident task lineage/process evidence `(tid, root_tid, submitter_tid, ancestry_tids, scheduling_class, connection_owner, host_processes, hostname)`). Unacknowledged launches also retain exact source/reserved queue names and original request ID. Updated at launch/handoff/reap; `LivenessMonitor` retains the latest checkpoint while any referenced reservation remains unresolved, even after Manager exit. |
| `weft.state.labels.<root_tid>.pending.<parent_tid>` (Manager-owned consume-on-dispatch index) | Compact pending tokens referencing accepted `weft.spawn.requests` rows submitted by `<parent_tid>` (`<submitter_tid>` when present, or `<root_tid>` for root submissions). Consumed (`delete(message_id=...)`) immediately when the referenced primary row is reserved for launch (or observed absent from `weft.spawn.requests`), so the queue empties and **auto-disappears in SimpleBroker** as soon as its children are dispatched. |

#### Lineage transport and pending-token contract

Use system-owned lineage in the spawn envelope and `RuntimeIdentity`: `root_tid`, `submitter_tid`, `ancestry_tids`, `scheduling_class`, and the canonical broker context:
- **Root submission (`submitter_tid=None`)**: derives `root_tid` from its committed request ID (or explicit TID) and sets `ancestry_tids = []`.
- **Nested same-context submission**: inherits `root_tid` from the caller's installed `RuntimeIdentity` and records the caller's `tid` as `submitter_tid`. If the caller's `scheduling_class == "finite"`, the child's `ancestry_tids` is `[*caller.ancestry_tids, caller.tid]`. If the caller is transparent for ordinary frontier scheduling (`scheduling_class in {"background", "internal"}`), the child inherits `caller.ancestry_tids` unchanged (or `[]` if the transparent caller had no finite ancestor).
- **Validated `scheduling_class`**: determined strictly by the Manager/launcher from authoritative validated sources (`"internal"` for trusted internal route/service/pipeline-stage-or-edge, `"background"` for validated `spec.persistent=True` or `spec.interactive=True`, and `"finite"` for all other ordinary tasks). The existing `metadata.get("role")` snapshot field is untrusted and does not distinguish `finite` from `background` tasks.
- Propagate `root_tid`, `submitter_tid`, `ancestry_tids`, `scheduling_class`, and `connection_owner` through wrapper and worker spawn transport (`weft/core/launcher.py`, `weft/core/runners/host.py`) before user code runs, and record them in the Manager's `task_spawned` event (`weft.log.tasks`) and the task's `weft.state.tasks.<tid>` snapshot. Application tags, process-title strings, and caller `metadata["family"]` or `metadata["role"]` grant no scheduling authority. Cross-context submissions are roots in the destination context.

Pending tokens written to `weft.state.labels.<root_tid>.pending.<parent_tid>` (where `<parent_tid>` is `submitter_tid or root_tid`) use one compact JSON wire contract:

```json
{
  "schema": "weft.family.pending.v1",
  "request_id": 1844674407370955161,
  "root_tid": "1844674407370955100",
  "submitter_tid": "1844674407370955120",
  "ancestry_tids": ["1844674407370955100", "1844674407370955110", "1844674407370955120"]
}
```

- `request_id` is the exact message timestamp/ID of the accepted request on `weft.spawn.requests` and serves as the logical ordering key (oldest `request_id` for FIFO root/sibling selection; newest `request_id` for LIFO child descent).
- `ancestry_tids` carries the immutable finite ancestor chain from `root_tid` through the nearest finite ancestor at submission time, bounded by finite nesting depth. Because `ancestry_tids` lives in the request envelope, the pending token, `RuntimeIdentity`, and `weft.state.tasks.<tid>`, a Manager can always resolve the nearest still-live finite ancestor in $O(\text{depth})$ even after intermediate ancestors (`B` in `R → A → B → C`) and old Manager checkpoints have exited and been deleted by `LivenessMonitor`.
- Every append to `.pending.<parent_tid>` receives a fresh physical SimpleBroker message ID (`label_message_id`), because SimpleBroker message IDs are globally unique across queues.
- Pending tokens never duplicate the full `TaskSpec` payload or substitute for `weft.spawn.requests`. One queue per `(root_tid, parent_tid)` avoids scanning unrelated families or siblings to find a frontier tip's children. Retain no dedicated broker connection or watcher per pending bucket. Unknown schema versions trigger bounded re-indexing from `weft.spawn.requests`, never speculative dispatch or deletion of primary work.

#### Acceptance, classification, and consume-on-dispatch lifecycle

The `weft.spawn.requests` write is the sole acceptance commit point. Pending-queue indexing happens after acceptance; an index write failure never turns an accepted TID into a submission error or triggers producer resubmission. Producers do not write `weft.state.labels.*` or maintain family counters.

On watcher activity, the Manager classifies newly observed `weft.spawn.requests` rows in bounded, resumable generator pages and appends a pending token to `weft.state.labels.<root_tid>.pending.<parent_tid>` where `<parent_tid>` is the request's immutable `submitter_tid` (or `root_tid` when `submitter_tid is None`). Keep the classification cursor separate from launch eligibility and continue classifying while admission is blocked or all W frontiers are occupied, so a deeply nested child behind a large root backlog becomes selectable. Parsing and indexing happen once per newly observed request in steady state, not once per dispatch.

In memory, the Manager maps each non-empty `.pending.<parent_tid>` bucket to its effective **scheduling parent** using `ancestry_tids` and the current live `finite` resident set:
- For a root bucket (`submitter_tid is None` or `ancestry_tids == []`), the scheduling parent is `<root_tid>`.
- Otherwise, the scheduling parent is the last TID in `ancestry_tids` that is currently a live `finite` resident, or `<root_tid>` if no ancestor in `ancestry_tids` remains resident. (Because transparent `background` and `internal` tasks do not append themselves to `ancestry_tids`, children submitted by transparent tasks automatically attach to the nearest live `finite` ancestor or `<root_tid>`.)

Manager-local in-memory maps cache active frontier stacks, resident task state `(tid -> (root_tid, submitter_tid, ancestry_tids, scheduling_class, contracted_parent_tid))`, and per-bucket pending `(request_id, label_message_id)` min/max sets so candidate selection uses bounded frontier scans and logarithmic in-memory indexes without rescanning queues on every turn:
- **Consume on dispatch**: When the scheduler selects a candidate `(request_id, label_message_id)` from `weft.state.labels.<root_tid>.pending.<parent_tid>` and admission allows launch, the Manager attempts the atomic exact-ID reservation `move_one("weft.spawn.requests", reserved_queue, exact_timestamp=request_id)`. Whether the move succeeds (this Manager reserved it) or returns `None` because the primary row is already absent (another Manager reserved it), the Manager **immediately deletes the pending token** (`delete(message_id=label_message_id)`) from `.pending.<parent_tid>`. When the last pending token in `.pending.<parent_tid>` is deleted, the queue is physically empty and **auto-disappears in SimpleBroker**.
- **Direct consumption on parent exit (no bulk token relocation)**: When a resident tip `T_tip` is proven exited via the existing scoped process/reap rules (`analyze_liveness` / child sentinel), pop `T_tip` from its frontier. **Never move or copy tokens out of `weft.state.labels.<root_tid>.pending.<T_tip>` on parent exit**, because relocating every queued token would make completion work $O(N)$ in `T_tip`'s backlog size. Instead, keep `.pending.<T_tip>` in place and update its in-memory scheduling-parent pointer and meld its indexes in $O(\log N)$ to `T_tip`'s contracted parent (the nearest live `finite` ancestor in `T_tip.ancestry_tids`, or `root_tid`). The frontier (Rule 6) or contracted ancestor continues consuming tokens directly from `.pending.<T_tip>` as each child is dispatched (`delete(message_id=label_message_id)`), and `.pending.<T_tip>` auto-disappears naturally when its last token is consumed.
- **Reserved return / explicit-TID repair**: An ID watermark alone is insufficient because explicit-TID submissions and returned reserved rows can appear below the classification cursor. When a reserved launch fails before spawn and `ReservedPolicy` returns the request to `weft.spawn.requests`, re-append its pending token to `.pending.<parent_tid>` immediately. In addition, run a bounded, resumable reconciliation pass over `weft.spawn.requests` on startup, after index errors, and periodically on the existing admission maintenance cadence (spread across turns rather than restarting at the head) to index any unindexed primary row and delete any orphaned pending token whose `request_id` is no longer present in `weft.spawn.requests`.

#### Launch handoff using the existing reservation and checkpoint

Keep the original request in its existing Manager reserved queue until recovery can rely on task-owned evidence or positive settlement. Reuse `_checkpoint_admission_launch` and `_checkpoint_spawned_admission`, replacing their budget fields with the lineage/class/process evidence above, on both backends. No new queue, receipt format, or family event log is needed.

1. **Checkpoint before launch, then record the process.** The existing pre-launch checkpoint must succeed before `Process.start()`. It retains the exact reservation reference and validated runtime identity. After launch, checkpoint scoped wrapper/worker evidence through the existing launch-result path; check publication success instead of treating it as best-effort. Retain unresolved entries in every subsequent Manager snapshot, including terminal snapshots. Publication failures retry in bounded maintenance as specified in Section 1.
2. **Acknowledge only at handoff or settlement.** A valid task-owned snapshot for the same TID, canonical context, lineage, scheduling class, and scoped runtime identity transfers recovery custody to `weft.state.tasks.<tid>`. Otherwise keep the reservation until existing positive launch-failure/whole-process settlement proof resolves it. Owner connection counts, startup fallback, a terminal event, or wrapper exit alone do not authorize acknowledgement or replay. Use this predicate in normal, synchronous, and stale-launch-result acknowledgement paths. Exact-delete the original reserved request first; only after confirming its absence may the launching Manager omit its checkpoint entry. A successor may acknowledge a resolved reservation but never writes the old Manager's task-state queue.
3. **Protect both halves from automatic cleanup and reactor spin.** The valid structural Manager checkpoint also records its ordinary source/reserved queue names and remains protected while any own ordinary reservation exists, including before the mandatory pre-launch checkpoint. A cold successor exact-requeues an unreferenced reservation from a positively dead current-protocol Manager only when no checkpoint launch reference or task-owned runtime snapshot exists for that TID; unknown protocol/owner or failed observations retain it. Retry claimed/blocked moves through bounded maintenance, respecting broker claim rules. Before retiring a Manager's newest checkpoint, `LivenessMonitor` checks its referenced reservations by exact ID. Any still-present reservation or uncertain read preserves that checkpoint, for both stale and unknown-timeout retirement; existing age, generation, and exact-delete rules still apply. TaskMonitor's reserved/dead-task cleanup must likewise preserve those reservations regardless of the Manager's terminal state or age, rechecking before deletion and leaving cleanup pending when custody is unresolved. In `weft/core/manager.py`, yield, shutdown, and reserved-policy paths (`_requeue_public_reserved_spawn_requests_before_yield` and `_apply_spawn_reserved_policy(..., message_timestamp=None)`) must not run bulk `reserved.move_many(...)` or `reserved.read_many(...)` across all rows in `T{manager}.reserved`; they must operate by exact `message_id` and requeue/clear only requests positively known not to have launched, retaining live or ambiguous launch custody so an already-launched task is never returned to `weft.spawn.requests` and launched twice. Likewise, because `T{manager}.reserved` is registered with `QueueMode.PEEK`, `Manager._has_pending_messages()`, `_manager_owned_work_pending()`, and `T{manager}.reserved` queue draining must ignore reserved rows already in launched/handoff custody so non-empty `T{manager}.reserved` custody does not trigger `MultiQueueWatcher._drain_queue()` `notify_activity()` spin loops or block idle timeout. These checks use checkpoint references and exact queue reads, not descendant scans. Once reservations are acknowledged, normal checkpoint retirement resumes. `LivenessMonitor` remains the sole task-state deleter.

If `Process.start()` succeeds but both post-launch checkpoint publication and task-state publication fail before the Manager crashes, the mandatory pre-launch checkpoint and reservation survive, but they cannot prove whether execution began. Preserve and diagnose that ambiguity through existing recovery handling; never infer safe replay from missing evidence. This plan does not add an atomic transaction between OS process creation and broker writes, or claim automatic drain for that ambiguous failure window.

#### Recovery and detached-process reconciliation

Reuse the existing detached-task bootstrap and bounded round-robin liveness reconciliation path in `weft/core/manager.py` (`_refresh_postgres_admission_evidence` / `_bootstrap_postgres_admission_evidence` / `_retire_admission_launches`), replacing budget-deficit tracking with frontier/lineage tracking:
- **Startup bootstrap**: Read `latest_task_state_rows()` (`weft.state.tasks.*`) to recover:
  1. Live detached tasks `(tid, root_tid, submitter_tid, ancestry_tids, scheduling_class, host_processes, hostname)` from task-owned snapshots,
  2. Prior or peer Managers' `scheduler_frontiers` checkpoints from `weft.state.tasks.<manager_tid>`,
  3. Unacknowledged launches from retained Manager checkpoints matched by exact request ID against Manager reserved queues, including launches whose task snapshot never appeared. `task_spawned` log events may corroborate evidence but are not required for custody or recovery, and
  4. Existing pending tokens in `weft.state.labels.*.pending.*`, reconciled against `weft.spawn.requests`.
- **Reconstructing frontiers and contracted pending buckets without Manager checkpoints or dead ancestor snapshots**:
  - Only live tasks with `scheduling_class == "finite"` occupy finite frontiers; live `"background"` (`spec.persistent` / `spec.interactive`) and `"internal"` residents are excluded from finite frontier stacks so recovering more than W background workers after a Manager checkpoint disappears never consumes finite frontiers or blocks ordinary work.
  - For each live `"finite"` task, its recovered `ancestry_tids` chain identifies every live `"finite"` ancestor in order (`[a for a in task.ancestry_tids if a in live_finite_tids] + [task.tid]`), reconstructing the exact active branch stack `[anchor_tid, ..., tip_tid]` even if intermediate ancestors exited and `LivenessMonitor` already deleted their `weft.state.tasks.*` snapshots and the prior Manager's `weft.state.tasks.<manager_tid>` checkpoint.
  - Likewise, each surviving `weft.state.labels.<root_tid>.pending.<parent_tid>` bucket attaches through the recovered ancestor chain to the last TID in its tokens' `ancestry_tids` that is in `live_finite_tids` (or `<root_tid>` if none is live). In `R → A → B → C` where `B` queued `C` and exited while `A` remains live on a frontier, `.pending.<B>` carries `ancestry_tids = ["R", "A", "B"]`, so recovery attaches `.pending.<B>` directly to `A`'s frontier tip and dispatches `C` under `W=1`.
- **Bounded maintenance**: During ordinary runtime after bootstrap, launch and reap events update local frontier and resident state immediately; detached tasks not in `self._child_processes` (inherited from a prior Manager) are checked in bounded round-robin batches (`MANAGER_ADMISSION_REFRESH_BATCH_SIZE`) using `analyze_liveness()` on their recorded `host_processes` (`(pid, create_time)`). Do not persist liveness verdicts or probe deadlines in queues (`[LIVENESS.R1]`). `LivenessMonitor` remains the sole component deleter of `weft.state.tasks.*` (`[LIVENESS.R3]`).

All `weft.state.labels.*` and `weft.state.tasks.*` queues remain excluded by the existing `weft.state.` runtime prefix from `dump`/`load`. Imported ordinary requests retain lineage (`root_tid`, `submitter_tid`, `ancestry_tids`) in their `weft.spawn.requests` envelopes and rebuild pending tokens through classification. No user intent, output, or launch-authorizing request exists only in runtime bookkeeping.

### 4. Multiple Managers and internal pipelines

Preserve [MANAGER.9]: atomic reservation authorizes each public launch; registry leadership does not. Do not add a global scheduler leader, distributed connection lease, or broker-private locking.

W=5 is a **local Manager bound**, not a claim of five branches across all processes. A task extending that Manager's current tip uses its existing frontier. A foreign-branch task requires a free local frontier. The union of ordinary resident work is covered by the retained ancestry paths of all owners, including dead Managers whose detached tasks still live (`weft.state.tasks.*`). Shared pending queues (`weft.state.labels.<root_tid>.pending.<parent_tid>`) improve discovery across Managers without granting exclusive family ownership. Actual connection measurement remains cross-process.

On failover, reconcile/adopt retained orphan branches from `weft.state.tasks.*` before admitting new roots; do not erase ancestor/path evidence when a Manager disappears. If restored responsibility exceeds W, drain it and extend existing branches, but create no additional independent branches until below the bound. Concurrent Managers may temporarily append duplicate pending tokens for the same `request_id` or choose different siblings; exact source reservation (`move_one` on `weft.spawn.requests`) still prevents duplicate launch, and the losing Manager deletes any stale pending token when its `move_one` misses. A strict context-wide W would require an additional shared ownership protocol and is not claimed here. The proof below states its stable-owner assumption explicitly.

Pipeline-owned stages and edges retain their existing trusted internal bootstrap and simultaneous residency. Do not put those siblings through the ordinary serial-branch rule. They inherit the public pipeline root's family. For ordinary children submitted by an internal stage/edge, contract trusted internal ancestry to the nearest ordinary ancestor and cache that scheduling parent; internal nodes are transparent for ordinary scheduling, but their connections remain in U. Such a child can extend its pipeline's frontier even when all ordinary frontier places are occupied. Caller metadata cannot request this treatment. Test a full window of pipelines whose stages each submit ordinary nested LLM tasks.

### 5. Explicit background lifecycles

Existing validated `spec.persistent=true` or `spec.interactive=true` marks a background resident (`scheduling_class="background"`, [TS-1]). Such a request uses the same primary queue, measured gate, and startup path. It temporarily uses a frontier while launching; after the startup gate clears through positive startup evidence or the bounded missing-snapshot fallback in Section 1, remove that background frame from the frontier stack and release/reuse its place. Its actual connections remain in U. Its validated `scheduling_class="background"` and lineage remain in the retained Manager checkpoint until task-owned snapshot handoff or positive settlement; releasing the frontier does not acknowledge its reservation. This is scheduling by existing lifecycle semantics, not another source or a child privilege.

A background ancestor is transparent when finding the finite child's scheduling parent. If there is no active finite ancestor, that child requires a free frontier; otherwise normal descent/sibling rules apply. Background tasks can therefore start beyond W without permanently blocking ordinary tasks, provided measured capacity remains. They receive no unmeasured allowance. Do not infer background status from `activity="waiting"`, silence, or elapsed time. An unmarked long-running one-shot still retains its frontier; expose the blocking TIDs and bound.

The finite-path bound and proof exclude explicitly declared background residents, whose resource use is a separate term below. Persistent tasks that indefinitely retain resources or spawn dependencies can still exhaust actual capacity. This policy preserves their existing lifecycle, not a universal liveness guarantee. Test more than W persistent/interactive residents followed by finite tasks and nested finite children, with enough measured capacity for all of them.

## Progress argument and its limits

### What is proved

Consider a finite set of accepted roots and their dynamically submitted descendants, with finite fanout/depth, terminating leaves, and no dependency from one sibling subtree onto an unstarted sibling or unrelated root. Child counts and the graph are not known beforehand. Assume ordinary tasks eventually submit their required descendants or complete, broker operations eventually succeed, reconciliation makes fair progress, and the number of retained Manager frontiers stays bounded.

Let P be the sum of retained frontier allowances across owners, including orphaned paths. Let H be an externally established upper envelope for the simultaneous connections along one complete finite root-to-leaf path in the tested workload. Let I bound internal runtime use, B bound explicit persistent/interactive residents, and E bound other server pressure. Startup transients and all wrapper/worker sessions must fit the respective terms. A sufficient condition is:

```text
E + I + B + P * H <= C - R
```

This is a proof/test condition, not a runtime reservation, task schema field, or debit. Shared ancestors make it conservative. The runtime neither forecasts all descendants nor charges H per task. H is obtained for the controlled test from its actual wrapper/worker topology and forced maximum connection-opening phases; a single historical sample is not a bound on arbitrary code. Under uncontrolled external load, the statement is conditional on capacity eventually returning to this envelope.

At most P finite branches can open sideways. Each branch may descend without needing a new frontier. Before a current tip reveals its child, its place remains occupied, so delayed submission cannot consume that branch's place with another sibling. Under the resource condition, a required next task along one of those paths can pass measured admission. Fair discovery and frontier turns eventually select it. A finite branch reaches a terminating leaf, releases real resources, and unwinds; known siblings then receive that frontier or a spare one. A later-discovered descendant can reenter without its exited ancestor consuming resources. Induction over the finite tree proves drain. FIFO admission protects older root IDs against newer root IDs; no finite latency is promised under permanent overload or an unbounded stream of caller-supplied older IDs.

For ops: rollup can exit after enqueueing enrichments, but its pending children remain in `weft.state.labels.<rollup_tid>.pending.<rollup_tid>` and `weft.spawn.requests`. Up to W spare frontiers can run enrichments concurrently in a single family. Each enrichment retains its frontier throughout any delay before LLM submission. The LLM extends that frontier and finishes, then the enrichment exits, and the frontier becomes reusable. Each pending token is deleted on dispatch, so the pending queues vanish automatically when drained. The backlog size does not enter the connection accounting or active-branch bound.

### Counterexample the implementation must prevent

With three resource units, launching rollup plus two enrichments leaves no room for either enrichment's LLM. LIFO over pending rows cannot fix that state. With one permitted frontier, the scheduler follows rollup → one enrichment → its LLM; the sibling cannot occupy that same frontier. With W frontiers, the resource envelope must accommodate W complete paths. W=5 is a policy default, not a mathematical guarantee under every connection ceiling.

### What is not claimed

Ancestry does not identify arbitrary joins. Sibling rendezvous, cross-family waits, opaque shell/process dependencies, unbounded recursion, and a single task exceeding the available resource envelope can stall. Adding a wait graph alone does not free retained connections. Supporting those cases with a hard progress guarantee requires a separate execution contract such as cooperative resource release, continuations, or declared/enforced demand. Keep these limits visible; do not silently convert them into an eight-slot forecast or claim universal deadlock freedom.

No proof is claimed for an unbounded sequence of Manager failures leaving live descendants, or for external clients permanently consuming the required capacity. Recovery tests must distinguish lost scheduling evidence from genuinely insufficient resources.

## Rollout and rollback

Use a coordinated runtime upgrade. Old live workers can still write `weft.spawn.children`, even after their Manager is replaced. Quiesce external producers and old Managers/workers before removing that source. Record all primary/child/internal source and reserved IDs and positive launch evidence first. Do not kill or redeploy production as part of implementing this plan without the corresponding operational authorization.

Provide a one-time migration through the existing recovery tools: recover old child-reserved rows using exact launch evidence; move remaining unlaunched child-source rows to primary using atomic broker moves that preserve IDs and bodies. Accept the old `submitted_by` envelope in the migration adapter and normalize it to lineage before first new dispatch. Missing ancestry is explicitly a root/unknown migration case; do not guess from task names. Verify no old producer remains and no child-source/reserved work remains before starting the new scheduler. A permanent child listener or silent fallback route is prohibited.

The one-time migration adapter is an explicitly invoked Manager subclass confined to the existing submission-recovery capability. It normalizes only delivery of inventoried legacy `{tid, context}` envelopes, before delegating to the same canonical validation, selection, measured gate, launch, checkpoint, and acknowledgement machinery. Atomic queue moves preserve original bodies and IDs; no replacement-body API or filesystem custody of accepted intent is needed. Unknown legacy ancestry is explicitly independent-root scheduling, recorded in the inventory, without guessing a family. The ordinary Manager has no legacy decoder. Reruns rebuild the cohort from retained primary/reserved requests, so the inventory is diagnostic rather than the sole surviving intent. The adapter follows normal Manager lifetime: finite migrated work drains naturally; persistent/interactive work can require ongoing operator supervision. It must not stop immediately after handoff, since normal shutdown terminates owned children.

Migration must be rerunnable by exact IDs and preserve ambiguous rows for reconciliation. Do not replay work already launched or rewrite TaskSpec TIDs. Retain a migration inventory sufficient to reverse queue placement for unlaunched work. Runtime `weft.state.labels.*.pending.*` queues are discardable only while stopped and after checking for active users, and rebuild automatically from `weft.spawn.requests`.

Rollback requires another quiescence point. Restore accepted unlaunched ordinary requests to the version's supported source representation without changing IDs, preserve results/reserved evidence, and remove/rebuild only runtime pending indexes. Do not run an old Manager against live new frontier ownership. Prefer a reviewed compatibility patch over a blind release revert; version/CI/dependency changes outside the admission experiment are not part of this plan.

### Architectural revision note (2026-10-14): detached task processes vs. relational label tables

During post-draft architectural review of the `weft.state.labels.*` design and subsequent peer-agent review of the simplified queue-native design, the following architectural issues were identified and resolved:

1. **Why detached child processes require broker-backed lineage (and why `Manager._child_processes` / OS `ppid` is insufficient)**:
   - In Weft, child tasks (`rollup → enrichment → LLM`) are never spawned as OS subprocesses of their submitting task; every task submits to SimpleBroker and is launched by the Manager (`weft/core/launcher.py::launch_task_process`). Moreover, ordinary user tasks run with `stop_with_parent=False` (`weft/core/launcher.py::_task_process_entry`) and intentionally survive Manager drain, idle exit, crash, or replacement ([MA-1], [MA-3]).
   - Because running user tasks live outside any successor Manager's OS process tree and `self._child_processes` map, lineage (`root_tid`, `submitter_tid`, `ancestry_tids`), validated `scheduling_class`, scoped process identity (`host_processes`), and active frontier state genuinely must be persisted in broker runtime state.
2. **Why the earlier `weft.family.v1` (`weft.state.labels.<root_tid>`) design turned SimpleBroker queues into relational tables**:
   - The previous draft stored four kinds of `member` rows (`accepted`, `launched`, `snapshot`, `terminal` with foreign-key `source_ref` pointers) plus versioned `frontier` rows and `state: "released"` tombstones in `weft.state.labels.<root_tid>`, and left `pending` rows unconsumed in `weft.state.labels.<root_tid>.pending.<submitter_tid>` until a four-condition family retirement fence ran a full reconciliation sweep and manually `exact-delete`d every row.
   - Because nothing ever consumed those queues on dispatch, SimpleBroker's natural property — that queues are created on write and **automatically disappear when emptied** — was defeated. Worse, `member` duplicated `weft.state.tasks.<tid>` (which `BaseTask._build_tid_state_payload` already writes with `submitter_tid` and `host_processes`, and which `LivenessMonitor` already deletes on task exit), and `frontier` duplicated Manager checkpoint state in `weft.state.tasks.<manager_tid>` (where `Manager._build_tid_state_payload` already checkpoints `admission_launches` for detached-task recovery in `_refresh_postgres_admission_evidence`).
   - **Resolution**: Keep detached running-task lineage (`root_tid`, `submitter_tid`, `ancestry_tids`, `scheduling_class`, `connection_owner`) in `weft.state.tasks.<tid>`, keep Manager frontier checkpoints (`scheduler_frontiers`) in `weft.state.tasks.<manager_tid>`, and make `weft.state.labels.<root_tid>.pending.<parent_tid>` a true **consume-on-dispatch queue** whose tokens (`weft.family.pending.v1`) are deleted immediately when the referenced primary row is reserved (or observed absent). Pending queues therefore empty and vanish automatically in SimpleBroker as children are launched, eliminating `weft.state.labels.<root_tid>`, `member`/`frontier` event logs, tombstones, and manual family retirement sweeps.
3. **Why immutable `ancestry_tids`, validated `scheduling_class`, direct bucket consumption on parent exit, and an explicit missing-snapshot fallback are required**:
   - **Surviving ancestry across dead intermediate ancestors (`R → A → B → C`)**: Pending references end at reservation, whereas ancestry must last as long as surviving descendants need it. If `B` queues `C` and exits while `A` waits for `C`, `LivenessMonitor` can delete both `B`'s `weft.state.tasks.<B>` snapshot and the old Manager's `weft.state.tasks.<manager_tid>` checkpoint. Carrying immutable `ancestry_tids` (`["R", "A", "B"]`) in accepted requests, pending tokens, `RuntimeIdentity`, and `weft.state.tasks.<tid>` lets a replacement Manager contract `C` directly to `A`'s occupied frontier under `W=1` without any family event log.
   - **Validated `scheduling_class` in `weft.state.tasks.<tid>`**: Existing `metadata["role"]` in task snapshots does not distinguish `finite`, `background` (`spec.persistent`/`spec.interactive`), and `internal` tasks. Persisting validated `scheduling_class` prevents >W live background workers from being reconstructed as occupied finite frontiers after a Manager checkpoint disappears.
   - **Bounded missing-snapshot fallback for the non-blocking startup gate**: Because `BaseTask._register_tid_state()` is best-effort, the startup gate defines an explicit 3-branch release rule (snapshot/owner usage observed, early process exit, or one retry after `MANAGER_ADMISSION_RECHECK_SECONDS` falling back to launch-time `RuntimeIdentity` + `process.pid` with diagnostic logging) so failed initial snapshot publication never stalls dispatch.
   - **Direct consumption of `.pending.<exited_tid>` on parent exit**: Moving all remaining tokens out of `.pending.<exited_tid>` when a parent exits would make completion work $O(N)$ in backlog size. Instead, parent exit updates the bucket's contracted parent pointer in $O(1)$ and continues consuming `.pending.<exited_tid>` directly as children are dispatched, so queue disappearance follows consumption without delaying the next launch.
4. **Why delayed reservation ACK requires exact-ID reserved-policy handling and excluding launched reservations from `QueueMode.PEEK` reactor activity**:
   - Keeping a launched request in `T{manager}.reserved` until `weft.state.tasks.<tid>` handoff (or settlement) interacts with two existing `weft/core/manager.py` assumptions that previously relied on immediate synchronous deletion in `_handle_child_launch_result`:
     1. `T{manager}.reserved` is registered in `self._queues` with `QueueMode.PEEK`, and `Manager._has_pending_messages()` (`weft/core/manager.py:4642–4662`) checks `_queue_has_pending()` across `self._queues` without filtering out `T{manager}.reserved`. Leaving launched custody rows in `T{manager}.reserved` would cause `_has_pending_messages()` and `_manager_owned_work_pending()` to return `True` on every turn and trigger `MultiQueueWatcher._drain_queue()` `notify_activity()` spin loops unless launched custody rows are ignored.
     2. `_requeue_public_reserved_spawn_requests_before_yield()` (`weft/core/manager.py:3886–3944`) and `_apply_spawn_reserved_policy(..., message_timestamp=None)` (`weft/core/manager.py:4970–5058`) currently run bulk `reserved.move_many` / `reserved.read_many` across all rows in `T{manager}.reserved` whenever `!self._has_active_child_launches()`. Under delayed ACK, they must iterate exact `message_id`s and touch only positively unlaunched requests so an already-running child awaiting handoff is never moved back to `weft.spawn.requests` and launched twice.
